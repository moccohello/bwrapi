# BWAPI 4.4 compatibility

In BWRAPI the in-game BWAPI server (`bwrapi_bwapi.dll`) fills the official BWAPI 4.4 `GameData` every frame, and bots attach with the official shared memory and pipe protocol (`Local\bwapi_shared_memory_*`, `\\.\pipe\bwapi_pipe_<pid>`, client version 10003). AIModule DLLs and client programs built with BWAPI 4.4 therefore run without changes. This document lists what is the same as BWAPI 4.4 and what differs.

Target: StarCraft: Remastered 1.23.10, x64 and x86 games. Everything below is the same for both bit widths.

## Works

- **Ways to run**: x86 AIModule DLLs (x86 loader), TournamentModule (its own loader), BWAPIClient programs, the Python client (`bwrapi.bwapi`). They attach to a running game.
- **x86 games**: the x64 and x86 servers have the same GameData and GameTable layout (`legacy44_layout_check.cpp` checks sizes and offsets in both builds), so the x86 loader, BWAPIClient programs and the Python client attach unchanged. The launcher looks at the game's bit width and injects the x86 server.
- **Sync and async**: in sync mode the game waits for the bot every frame, as in BWAPI. In async mode the game does not wait: after the bot responds, its commands run on the first following frame and that frame is handed to the bot (the bot receives frames with gaps). The mode is chosen per connection, when the client connects.
- **Unit commands**: every BWAPI `UnitCommandType` runs as a game command (attack, move, stop, build, train, research, upgrade, gather, repair, load, unload, morph, burrow, cloak, siege, lift, and so on).
- **Game commands**: `pauseGame`, `resumeGame`, `leaveGame`, `restartGame`, `setLocalSpeed`, `setFrameSkip`, `printf`, `sendText`, `setScreenPosition`, `setAlliance`, `setVision`, `pingMinimap`, `setRevealAll`, `setMap`. Commands are accepted while the game is paused, so a bot can `resumeGame` from inside a pause. `leaveGame` calls the game's `end_game(4)`, like Quit in the game menu, so the match ends and the replay is saved.
  - `setAlliance` runs only in a match and `setRevealAll` only in a replay. `setVision` shares vision in a match and shows that player's vision in a replay.
  - Outside network games, `sendText` turns the known cheat strings (`power overwhelming` and the others) into the game's cheat commands as the official server does (one-shot cheats and toggled cheats are handled as officially), and shows other lines in the message area under the local player's name.
- **Chat commands**: while a client is connected, the official BWAPI chat commands the local player types (`/leave`, `/speed [n]` (-1 without an argument), `/fs [n]` (1 without an argument), `/cheats`, `/restart`, `/nogui`, `/grid`, `/fps`) are run by the server through the game command path, like the official `parseText`, and are not passed to `onSendText`. The confirmation messages ("Changed game speed" and the others) are the official texts, printed through the `printf` path. The `/grid` grid and the `/fps` display are drawn with the other shapes in the same form as the official `updateOverlays`. `/wmode` and the official _DEBUG-only commands (`/latency`, `/test`) are not supported.
- **Events**: `onStart`, `onEnd`, `onFrame`, `onUnitCreate`, `onUnitDestroy`, `onUnitMorph`, `onUnitRenegade`, `onUnitComplete`, `onUnitDiscover`, `onUnitEvade`, `onUnitShow`, `onUnitHide`, `onPlayerLeft`, `onNukeDetect`. Unit events come in the same order as the official GameUnits.
  - `onSendText`: while a client is connected, lines the local player types in the chat box are not sent; lines that are not one of the chat commands above go to the client (the chat box closes as with Escape).
  - `onReceiveText`: received chat is delivered as that player's line, taken from the chat commands the game records in its replay recording buffer (with the sending player's number). In a replay it is delivered when playback reaches that frame. As officially, it arrives only while the `UserInput` flag is on, and in a replay, which has no `self()`, lines from every player arrive.
  - `onSaveGame`: when the local player saves through the game's save dialog (including the overwrite confirmation), it arrives with that save name on the next frame (on the next pause round while paused), before the other events of that frame. As officially, it reaches only the player who saved, not the other players of a network game.
- **Battle.net**: `isBattleNet()` is true when the game's network provider is Battle.net (`BNET`, or `BNAU` for matchmaking). In network games, `getLatency()` maps the game's latency setting (Low, High, Extra High) in the official order to Lan/Battlenet Low, Medium and High.
- **Drawing**: `draw*` shapes and text (Screen, Map and Mouse coordinates, BWAPI colors, text color codes and alignment) are drawn into the game screen as officially. They appear above the game screen and the console and below the cursor, and are captured by window captures (PrintWindow). This is the same in windowed mode and both full-screen modes; text is placed on glyphs made at the scale the game draws the screen with. `setGUI(false)` stops screen updates as officially, so shapes are not shown either.
- **Input**: with the `UserInput` flag on, the key and mouse button states of the game window and the mouse position are provided.
- **Remaining latency**: `getRemainingLatencyFrames()` and `getRemainingLatencyTime()` count from the game's last sent turn, as officially: the latency in frames minus the frames since that turn, and the latency time minus the ms since then. The game sends a turn right before it advances a frame and also while paused, so during a pause the values equal the latency.
- **Local settings**: `setLatCom`, `setGUI`, and `enableFlag` on frame 0. `setGUI(false)`, as officially, ignores `printf` and `setScreenPosition` and stops the game's screen updates (the match and the bot's frames keep going). The official large frame skip would keep the game loop from returning to window messages and so block the server's frame hook; instead, the game loop's screen update limit is set to an interval no update can pass, and `setGUI(true)` restores the original value. While the GUI is off, the game loop runs without waiting and uses one CPU core. As officially, the GUI is turned back on at the start of every match. `setCommandOptimizationLevel` (0 to 4) groups compatible unit commands of the same frame into one game command, with the same rewrite, exclusion and split rules as the official `CommandOptimizer`: attacks on enemy units, gathering, rally, Infestation and moves are rewritten as right clicks; Carrier and Reaver production is unified to a placeholder type; siege, cloak and burrow `Use_Tech` become the concrete command the unit's state calls for. Level 1 does not group buildings, levels 1 and 2 do not group position commands, and level 4 snaps positions to a 32-pixel grid to merge nearby commands, turns unit-target techs into position techs, and drops the partner of Archon and Dark Archon merges so they group. `Load`, `Attack_Unit`, `Unload_All` and `Cancel_Morph` are split into groups by whether the unit is a building, and the remaining `Use_Tech` by siege, cloak and burrow state. Grouped commands run, as on the official server, as one game command after selecting 12 units at a time, and duplicate commands for the same unit in the same frame stay in the group, as officially.
- **Latency compensation**: like the official server, the server keeps the unit commands handed to the game in a frame buffer in the form the client wrote them (before optimization), and re-applies the official `CommandTemp` effects to the projected GameData every frame until the game executes the command (the remaining latency frames). Example: after `gather`, the worker's target and `MoveToMinerals` are visible on the following frames too. The later stages (order, finish) of cancels, `Halt_Construction`, `Morph` and `Build_Addon`, and the resources and supply that `Train`, `Morph` and `Build_Addon` hold until the frame the game takes them, are also as official. With `setLatCom(false)` or for queued (shift) commands, nothing is applied. The buffer is cleared at match boundaries and when a client reconnects.
- **Information about other players**: like the official server, when `CompleteMapInformation` is off (it is always on in replays), information about other players is hidden.
  - Units (`UnitUpdate.cpp`): for units the bot does not own, production and internal values (`getTrainingQueue`, `getBuildType`, `getTech`, `getUpgrade`, remaining train, research, upgrade and build time, `getEnergy`, rally, `getTransport`, `hasNuke`, `isHallucination`) are the official defaults. For units that are visible but not detected, hit points, shields, timers, orders, targets, relations and state values are the official defaults too (resources, acid spores, `isGathering` and `isInvincible` keep their last values, as officially). `getRemainingTrainTime` of a Hatchery, Lair or Hive is the larva countdown in every state. A living unit that became inaccessible (it disappeared into the fog) has the official inaccessible defaults from that frame until it is seen again (`exists=false`, type `Unknown`, position `Positions::Unknown`, neutral player, `isVisible` and `isDetected` all false). A destroyed unit keeps its last frame's values, as officially, and only `exists` and `isSelected` become false, so its type and owner can be read in `onUnitDestroy`.
  - Players (`PlayerImpl::updateData`): for enemies, minerals, gas, gathered amounts, repair and refund statistics, upgrades, techs, producible units, supply, scores, `deadUnitCount` and `killedUnitCount` are 0. An upgrade level is shown only if a completed unit that uses that upgrade was visible on the previous frame. The neutral player has 0 for resources, upgrades, techs and producible units. Enemy start locations are `TilePositions::Unknown` outside replays (the official server sets them at match start while the flag is off).
  - Unit counts (`GameUnits.cpp`): `allUnitCount`, `completedUnitCount` and `visibleUnitCount` count the units the bot can see (revealed units), not the game's counters.
  - Unit types: Mineral Field Type 2 and 3 are `Resource_Mineral_Field`, and a Zerg building in a morph order has the type it is morphing into (a Hatchery morphing into a Lair is `Zerg_Lair`). This applies to unit types, unit counts and events alike.
- **Visibility and bullets**: `isVisible`, `isDetected` and `visibleUnitCount` follow the official rules (sprite visibility, detection conditions for units that need detection, the tiles around a Scanner Sweep). Outside `CompleteMapInformation` and replays, a bullet `exists` only while it is visible, and its `isVisible` is the visibility of the tile under it.
- **`getAPM()`**: counted from the commands the server hands to the game, with the official APMCounter formula (exponential decay over 0.95 minutes, 42 ms per frame). The selection and command counts are those of the official optimizer: one selection and one command per ungrouped command (a merge selects two units once), and one selection and one command per 12 units of the same key and split for grouped commands.
- **Repair and refund statistics**: `Player::getRepairedMinerals()` and the others count the amounts moved by the same game commands the official version hooks: the payment of one repair step, the full refund for cancelling a unit, a training queue entry, an egg or a cocoon, the 3/4 refund for cancelling a building or a Zerg building morph, and the refund for cancelling research or an upgrade. In replays they are counted when playback executes that command.
- **Unit indexes**: a game the launcher starts with `--game` runs with the SC:R extended unit limits turned off (1700 units, 100 bullets), so BWAPI unit indexes match the game one to one. In a game started with the extended limits (3400 and 400), the server still fills BWAPI's 1700 slots correspondingly.

## Still different

- **No `bwapi.ini`, no auto-menu**: there is no `bwapi.ini` and the server does not drive the game menus. The user starts the match (or the bot attaches to a match already in progress). The launcher options and product settings ([launcher guide](../python/bwrapi/launcher/README.md)) take the place of the ini entries.
- **AIModule DLLs run outside the game**: an AIModule DLL is loaded by the x86 loader, a separate process that connects to the in-game server as a BWAPI client, not into the game process. A TournamentModule runs in its own loader the same way. The bot's working folder (and so its relative `bwapi-data` paths) is the loader's working folder, the product `directory`.
- **Chat lines**: chat capture walks the recording buffer from the moment a client connects and turns it on. Lines received before that are not delivered.
- **Latency compensation in async mode**: the official server always waits for its client, so it has no async mode. When an async client skips frames, the commands received in between are placed using the remaining latency of the last projected frame, so their effect can end slightly before the game executes them.
- **Command re-check**: the official server checks received commands again with `canIssueCommand`; this server does not. The C++ and Python client libraries run the same check against the same frame's values before sending, so in sync mode the result is the same. In async mode, a command whose state changed in between is handed to the game and also counts toward APM.
- **Nuke target**: officially, the target of the Ghost's `NukePaint` order is remembered as the nuke target, but this game goes straight from `CastNuclearStrike` to `NukeTrack`, so the `CastNuclearStrike` target is used too. `onNukeDetect` and `getNukeDots` therefore give the actual target.
- **First-frame rule**: officially, on frame 0 neutral units count as accessible and detected even when not visible. A server attached before the match applies the same rule on frame 0, matching the official behavior; a server attached during a match applies it on the first match frame it produces after attaching.
- **Drawing look**: the official version draws pixels and bitmap fonts into a 640×480 8-bit screen buffer, while the server draws with the SC:R renderer: shapes are triangles in game pixels (circles and ellipses are polygons), and text uses the game UI font (including Korean) with an outline. Characters missing from the game font are not drawn. The amount that can be drawn in one display frame is limited by the free space in the game's vertex buffer and queue (about 10,000 rectangles).
- **Command results**: the server does not return command results to the bot. As in BWAPI, `true` means the command was handed over; its effect shows in the values of later frames. Commands that could not be executed are logged in the server log (`bwrapi_bwapi.log`, next to the server DLL) as `[command] status=not_executed`.
- `getLastEventTime()` is 0 for ordinary clients, as officially. In a Tournament it is the elapsed time (ms) of the previous AI callback.

## If you find a problem

If a bot behaves differently than in the original BWAPI 4.4 environment, check that it is not in this list, then open an issue with the information listed in [Issues and contributing](../README.md#issues-and-contributing).
